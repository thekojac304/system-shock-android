2. DELIBERATE STATIC DOOR POLICY
The AUTHOR1E compiler models every animated door cell as closed for generated
light, in every actual animation frame. A relation requiring an unresolved door
crossing is absent from the runtime receiver list. Opening a door does not grant
cross-room light; closing cannot leave stale generated spill. Relations that
remain valid wholly within the static topology can still receive light near a
door. The runtime carries the conservative portal dependency bitmask for QA but
does not use it to open crossings. Log reason:
portal-crossing-generated-light-disabled. Normal GPU geometry, gameplay and
original scalar/transient lighting are unaffected. This is an intentional
GENERATED1 product restriction, not a claim of animated-door validation.

3. PROFILE COMPILER, FORMAT AND LOADER
scripts/compile-horror-generated.py takes accepted level-{1,6}.generated.json,
level-{1,6}.partial.json, reviewed rules.json and the ignored owned ARCHIVE.DAT.
It verifies the level, source baseline, rules signature and closed-door model,
then compiles only levels 1 and 6. scripts/build.ps1 regenerates both QA assets
when all inputs exist and rejects stale assets when an input is missing. Binary
assets stay ignored under AndroidProject/app/src/qa/assets/horror-generated/;
verbose diagnostic JSON and proprietary art/archive bytes are never packaged.

Format HG1P version 1: fixed header with level, bounds, accepted baseline/rules
SHA-256 signatures and CRC32 body; 4096 map geometry keys; 4096 region IDs;
region/default ambient RGB; bounded light array with position/RGB/intensity/
radius/material/object IDs; sorted SurfaceIds and up to four relationships each;
full/partial status, up to two convex polygons of up to eight world-space
half-planes and 64-bit portal dependency mask; ten 256-byte emissive index rows.
Compiled sizes: Medical 209410 bytes / 265 lights / 1653 effective surfaces /
434 regions; Executive 195382 bytes / 179 lights / 1589 effective surfaces /
225 regions. The runtime validates version, accepted signatures, checksum,
bounds, sorted IDs and payload; it compares the complete live 64x64 geometry-key
array each generated frame. Any load or map mismatch applies NEUTRAL GPU to the
entire frame/profile, without partial generated data or gameplay changes.
Other levels always use neutral GPU in the GENERATED selector.

4. SURFACEID RECEIVERS AND PARTIAL SHADER
Existing emitted SurfaceIds are binary-searched in the compiled profile. Only
exact geometry/neighbor keys match. A full relation evaluates the existing
squared radial falloff; blocked/unsupported or missing relations add nothing.
Partial polygons are compiled offline into world-space inward-guarded planes.
The GLES fragment shader tests interpolated world position against at most two
convex polygons per light, at most eight planes per polygon and four lights per
draw. No runtime geometry traversal, ray tracing, shadow map or extra draws.
AUTHOR1E's accepted 4-polygon representation is preserved as offline evidence;
these two exact compiled levels use at most two and fail compilation if exceeded.
No dynamic shadowing by movable objects is claimed.

5. EMISSIVE MASKS AND ARCHETYPES
The ten reviewed source-index rows cover texture IDs
20,35,36,82,101,144,185,215,216,217. Indexed texture pixels are unchanged;
palette lookup still determines base color. In GENERATED, a reviewed mask texel
is self-lit and its housing follows normal illumination, independent of whether
the fixture's source casts a local light. No global threshold or whole-texture
emissive flag is used in this mode. GPU PROOF keeps its prior behavior.
Medical uses cold clinical RGB(.72,.88,1)*.16; Executive warm-neutral
RGB(1,.88,.76)*.16, with their existing generated lights and original live
darkness. No proof lights, warm Medical alcove override, Executive room light,
blanket ambient lift, fog or dynamic atmosphere was introduced.

11. KNOWN VISUAL AND AUTOMATION LIMITS
Static closed-door topology can leave an open doorway unnaturally dark. Other
levels, unsupported/complex terrain and arbitrary dynamic geometry have no
generated light. A changed map key disables the whole profile until it matches
again. The mask/shader is bounded, but visible fixture review covered only
the encountered subset of ten masks and limited camera angles; all ten have
exact offline index rows, not ten live visual passes. Partial boundaries looked
clean in these views, not at every angle. A dedicated off-by-default colored
debug overlay was deferred; logs expose load reason, source/receiver bounds,
draw counts and partial-reference counts. The source fixture/object IDs and
portal dependency bits remain available in compiled data for deeper QA.
Original scalar/transient effects remain; no new event integration was tested.

12. DECISION AND NEXT ART PASS
Keep the generator as an ordinary-area starting layer, subject to user visual
acceptance. Current estimate after live review: roughly 45-55% automatic /
45-55% manual setup, LOW confidence from two decks and three fixed views. The
strong Scene A and sparse Scene B argue for generated obvious fixtures and safe
static receivers, then manual level grading/contrast, selective later fog,
important doorway/space overrides and a few hero-room lights. Do not extend
inference research or animated-door propagation before the user reviews this
APK. Static no-cross-door spill is provisionally acceptable for this visual
prototype; whether it is acceptable in the final art is the user's decision.
